# Known Follow-Ups - Not Built, Documented for Whoever Continues This

Smaller items identified during a review of the codebase, deliberately left unbuilt per direction to focus on documentation and readiness assessment rather than opening new work. None of these block using or evaluating what's already built - they're refinements worth picking up next.

- **No `retry_attempted` field.** If a ticket ultimately fails even after a retry, nothing in the returned result distinguishes that from failing on the first attempt without a retry ever happening. Only visible in logs currently, not in the structured result itself.
- **`MAX_ASSESS_RETRIES` is defined but not actively enforced by a loop.** The cap-to-one currently holds only because of how the function is structured (it calls the assess step once, then at most once more) - not because anything checks the constant. Would silently do nothing if the retry logic were ever refactored into an actual loop without someone remembering to wire the constant in.
- **Repo-targeting mechanism is unconfirmed.** `devin_client.py` embeds the target repo as text at the start of the prompt, not via a confirmed, dedicated API parameter. This has only ever been tested against one repository. Worth confirming directly with whoever administers the Devin↔GitHub org connection before trusting it against a second repo.
- **No persisted link back to the full Devin session, possibly worth doing.** The harness only captures structured_output; Devin's full narrative report (file citations, resolved contradictions, reasoning) exists only in its web app. Confirmed on EX-65: the full report traces nine files by line number and resolves a real contradiction in the ticket's premise, but structured_output compresses that to a paragraph each. DevinStepResult (devin_client.py) already carries session_id internally - it's just never surfaced into the result dict returned by run_assess_only()/run_harness(). No new logic needed, just thread the existing field through.
- **`jira_status` is informational only, not gated on.** The field exists and warns when a ticket is already Done/Closed, but nothing in the actual validation logic currently changes behavior based on it - worth deciding whether it should, and what "verify a claimed fix" mode would actually look like if built. Confirmed as a real, not hypothetical gap: running a real, closed ticket through assess (EX-42, run manually while testing) showed Devin has no way to know a ticket was already resolved unless this is explicitly surfaced - it investigated a "Done" ticket as if it were a live, open bug.
- **Manual checkpoint-override scripts are one-off and ticket-specific**, not a general tool. Two exist, each hardcoded to one specific test ticket's exact assessment. If this pattern is kept for future testing, worth generalizing into a single reusable script rather than writing a new one per ticket.
- **CI verification can't distinguish "no CI configured on this branch" from "CI ran and genuinely failed."** Confirmed with a real test: a target branch with no check-runs configured at all returns `"unknown"` from GitHub, which is still treated as a mismatch against Devin's claim - correctly cautious, but not the same signal as a real failure. Worth adding a distinct status (or at minimum a clearer message) for "no CI exists here" before relying on this in a real integration, so a missing config doesn't look identical to broken code.
